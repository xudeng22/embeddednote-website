浏览器里的预览是对的,屏上不对。多数人第一反应是回去改抖动算法,而这一步通常是错的。

一张图从文件变成颜料,中间经过五层:源像素、调色板映射、字节打包、驱动与波形、面板本身。每一层出错时,画面的"形状"是不一样的。先看错的形状,再看代码,能省掉大半时间。

## 先看症状

| 你看到的 | 该怀疑哪层 | 先做哪个测试 |
| --- | --- | --- |
| 整屏偏色,但形状正确 | 调色板映射 | 每个索引显示一块纯色 |
| 斜切、重复列、镜像、反色 | 打包与布局 | 5 × 2 奇数宽度向量 |
| 文字出现噪点、渐变断层 | 抖动与色调 | 换成最近邻再转一次 |
| 颜色对但对比很平,或上一帧隐约可见 | 驱动与波形 | 从已知上一帧强制全刷 |
| 只有一条带、一个角,或两台机器结果不同 | 面板与环境 | 换一台、换一个温度 |

这个顺序按"排除成本"排,不是按概率排。如果形状是对的、只有颜色不对,就别再读打包代码了。

## 原因一:你转的不是你以为的那张图

浏览器会静默缩放。canvas 的尺寸可能由 CSS 决定,也可能由 `width`/`height` 属性决定;EXIF 方向可能应用了,也可能没有;界面上的"裁切"在缓冲区里可能变成了补边。

**一分钟检查**:把预览 PNG 导出,读它的真实像素尺寸,必须**正好等于面板分辨率**,而不是原照片的尺寸。然后把源图按 1:1 打开,确认你预期的区域就是实际到达的区域。

**处理**:先按面板长宽比裁切,再转换;不要在转换后拉伸。拉伸会多一次重采样,让后面所有对比都失去意义。

## 原因二:调色板是参考色,不是面板的原生色码

每个转换工具都自带一套调色板:黑、白、红、黄。这些是"在显示器上看起来合理"的 RGB 值。控制器存的不是 RGB,它存索引;面板的波形把索引变成一种颜料状态。同一块屏上索引 3 是红色,换一块可能完全不是。

**一分钟检查**:做一张"每个索引一条纯色块"的测试图(索引 0 到 7,每条带标注),转到屏上看。如果两条颜色互换了,问题在映射,不在抖动。

**处理**:建一份实测配置,把控制器的**原生色码**和你在**明确光源下测得的 sRGB 值**分开记录,再按这份配置做量化。[图像转换器](/zh/tools/epaper-image-converter/)可以直接导入这份 JSON,那一页的色板表也写清了哪些是参考预设、哪一个是设备配置。

## 原因三:打包方式和驱动对不上

这一层出问题时画面最夸张,也最好认。四件事必须一致:

- **行跨度**:控制器要求每行补齐到字节、字,还是不补齐?
- **四位顺序**:4 位模式下,一字节里第一个像素在高四位还是低四位?
- **遍历方向**:从左到右、从上到下,还是旋转 90°、或者 X 轴镜像?
- **极性**:1 是黑点还是白点?

**一分钟检查**:还是那个五像素宽的向量。

```
第 0 行:  0 1 2 3 4
第 1 行:  5 0 1 2 3
```

连续行优先 RAW4、高四位在前、不补齐,结果是 `01 23 45 01 23`。注意 `0x45`:高四位是第 0 行最后一个像素,低四位是第 1 行第一个像素。如果驱动把每行补齐到整字节,就会变成六个字节。这一个字节的差别,在屏上就是一条斜切。

**处理**:定一套约定,写进接口文档,让打包器和驱动引用同一张表。不要靠"调一下偏移"来绕——错误只会移动,不会消失。[RAW4 校验指南](/zh/articles/epaper-palette-raw4-packing-guide/)里有完整的推演,包括奇数宽度的情况。

## 原因四:抖动算法和内容打架

Floyd–Steinberg 用在界面上会毁掉小字;最近邻用在大面积渐变上会出现断层。两个算法都没错,是用的地方错了。

**一分钟检查**:同一张图转两次,一次最近邻 + 边缘保护,一次 Floyd–Steinberg。如果第二次文字糊了、第一次清晰,原因就找到了。如果两次都糊,问题在更上游。

**处理**:按内容选,不按喜好选。界面和文字用最近邻 + 边缘保护,照片用误差扩散,需要"每次刷新图案都一样"时用有序抖动。

## 原因五:刷新模式与波形

局刷和全刷用的是不同的波形。如果切换模式前没有清屏,或者上一帧还有残留时就写新帧,即使每个字节都正确,颜色也可能发灰或偏移。

**一分钟检查**:强制从已知的上一帧做一次全刷,再显示新帧。如果结果正确,说明缓冲区没问题,是模式的问题。

**处理**:换调色板、换波形、换旋转之后,一律先做一次全刷。局刷是省电和降延迟的手段,不是"跳过第一次全刷"的理由。取舍在[残影那篇](/zh/articles/epaper-ghosting-causes-and-fixes/)里展开。

## 原因六:面板和房间

温度决定颜料移动的速度。观察光源决定"白"看起来有多白。不同批次的屏,差异可能比两个固件版本还大。FPC 没压好,会出现一条和"行跨度错误"一模一样的带。

**一分钟检查**:换一台同型号的机器,再换一个温度,看同一帧。如果错误跟着硬件走、不跟着固件走,剩下的就是物理层。

**处理**:软件层面没有处理办法。记录条件,修改你的结论,而不是改代码。

## 提 bug 之前先写清这些

大部分电子纸 bug 报告没法用,因为里面只有一张照片和一句抱怨。把下面这些写全,一轮就能得到答案,而不是五轮:

```
panel_model:            面板型号
controller:             控制器型号
waveform / LUT version: 波形/LUT 版本
firmware commit:        固件提交
palette id or profile hash: 调色板或配置哈希
buffer format:          RAW4 / RAW8,行跨度,四位顺序
dimensions:             分辨率
first 16 bytes (hex):   前 16 字节
photo conditions:       光源、距离、温度
what you expected:      预期
what appeared:          实际
```

前 16 个字节,通常能在任何人打开数据手册之前,就把打包的争论结束掉。

## 这篇是什么,不是什么

分层模型和这些测试属于工程实践,不是一次测量活动。本文没有为某块具体面板做特性测试,文中字节数都是算术结果。六个原因的顺序是按"每个测试比后一个便宜"排的——关于概率,我们只做这一个声明。

如果你还在选硬件,先读[电子纸完整工程指南](/zh/articles/epaper-engineering-field-guide/):这里一半的失败,在你决定面板、控制器和传输格式的时候就已经注定了。

## 六个原因之外的三个问题

### 全刷时正常、局刷后就错,算哪一个原因?

都不算——流水线本身没问题。局刷用的是另一套波形,在全刷模式下正确的映射和打包,到局刷下可能偏淡或偏色。别动打包代码:先做一次全刷,再确认这个温度下支不支持局刷。

### 色块对了,但照片发灰,是调色板还是抖动的问题?

色块对说明“索引到颜色”的映射是对的。发灰通常是色调问题:亮度和对比度在量化之前就作用了,而一张照片映射到六个参考色,饱和度必然下降。用最近邻、关掉色调调整再转一次;如果还是平的,那是调色板的上限,不是算法的问题。

### 只盯着屏幕看,怎么区分行跨度错误和四位顺序错误?

跨度错误会把画面斜着拉开:内容还认得出,但每一行比上一行多偏一点。四位错误是相邻像素互换,所以会看到两像素宽的条纹或颜色交替,几何形状仍然是正的。用 5 × 2 那个向量,一帧就能分开。
