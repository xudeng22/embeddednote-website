所有"BLE 吞吐计算器"都是模型。真正有用的不是它给出的数字,而是这个数字建立在哪些假设上。这篇把我们工具里的算术逐行摊开,你可以拿去核对,也可以自己在表格里重算一遍。

算例用默认参数:240 KB 应用数据、MTU 247、LE 2M PHY、连接间隔 30 ms、事件长度 15 ms、链路加密。

## 第一步:从 MTU 到每次操作的有效字节

ATT 要占 3 个字节放操作码和属性句柄,所以 247 的 MTU 实际能带 244 字节的值。如果应用自己还要在这个值里放头部(分包序号、偏移),现在就减掉,因为它每次操作都会重复:

```
value   = min(MTU − 3, 编码器单包上限)
payload = value − 应用头
```

MTU 247、无应用头时,每次写带 **244 字节**。240,000 字节就是 `ceil(240 000 / 244) = 984` 次写操作,最后一次只有 148 字节。

这是第一个常见的出错点:用文件大小除以 MTU(而不是除以有效值),算出 972 次,少算了 1.2%。

## 第二步:一次操作在空口上花多少时间

一次 ATT 写不会单独上路,一个链路层 PDU 里还要装 L2CAP 头和 ATT 头:

| 字段 | 字节 |
| --- | ---: |
| L2CAP 基本头 | 4 |
| ATT 操作码 + 句柄 | 3 |
| GATT 值 | 244 |
| **链路层载荷(数据)** | **251** |
| MIC(仅加密链路) | 4 |

251 正好是 Data Length Extension 的上限,而 MIC 是**算在这个上限里面**的,不是加在外面。所以一条加密的 MTU-247 链路塞不下一帧:它会拆成两个 PDU,分别携带 247 和 4 字节数据。关掉加密,同一次写只需要一个 PDU。

每个 PDU 外面还有一堆不是数据的东西:前导(2M 下 2 字节)、接入地址 4、链路层头 2、CRC 3、对端的一个空确认,以及两段 150 µs 的帧间隔。

在 LE 2M 下,一次"写 + 确认"(带上面的两 PDU 拆分)约 **1,812 µs**;LE 1M 下是 **2,992 µs**。

## 第三步:一个连接事件能装几次

这个量级下,瓶颈通常不是射频,而是调度。15 ms 的事件里:

- 15,000 µs ÷ 1,812 µs ≈ 2M 下最多 8 次
- 15,000 µs ÷ 2,992 µs = 1M 下最多 5 次

但模型还假设主机和控制器一个事件只流水 **4** 次写操作——这是对手机实际行为的保守替代:

```
per_event = min(floor(事件长度 × 1000 / 单次 µs), 每事件写次数上限) = min(8, 4) = 4
events    = ceil(984 / 4) = 246
总时长    = 246 × 30 ms = 7 380 ms
```

**7.38 秒**。不是"240 KB ÷ 1 Mbps ≈ 1.9 秒"。

## 最反直觉的一个结果

同一个算例,把 PHY 从 2M 换成 1M:

| | LE 2M | LE 1M |
| --- | ---: | ---: |
| 每次写 + 确认的空口时间 | 1,812 µs | 2,992 µs |
| 15 ms 事件内可容纳 | 8 | 5 |
| 每事件允许的写次数 | 4 | 4 |
| 需要的连接事件数 | 246 | 246 |
| **30 ms 间隔下的总时长** | **7.38 s** | **7.38 s** |
| 实际占用空口时间 | 1.78 s | 2.94 s |
| 有效吞吐 | 1.08 Mbit/s | 0.65 Mbit/s |

2M 把空口时间砍掉 40%,**总时长一点没变**,因为卡住的是"每事件 4 次"这个上限。把上限提到空口允许的 8 次,同样的传输变成 **3.69 秒**——2 倍提升,任何 PHY 都给不了。

如果你的估算结论是"换 2M 就能快一倍",那这个模型漏掉了事件上限。这是 BLE 吞吐说法里最常见的一个错误。

## 模型故意不算的东西

- **控制器调度。** 真实控制器自己决定一个事件能塞几个 PDU,手机通常很保守。
- **主机队列。** iOS 要用 `canSendWriteWithoutResponse`;Android 的写队列深度按厂商不同。
- **接收端成本。** 一旦射频够快,Flash 页写入、文件系统提交、应用处理往往才是大头。
- **重传。** 工具里的重传百分比是线性惩罚,不是误包率模型。
- **连接参数中途变化。** 对端可以重新协商,有些手机确实会。

这些任一项都能让实测值上下偏 2 倍,所以那一页写的是"估算",不是"吞吐率"。

## 怎么用它校准现实

测一次,然后只调两个数:每事件写次数、重传百分比。其余都是规范推导出来的,应该只差几个百分点。

一次可用的测量要记录:手机型号与系统、协商后的 MTU、实际 PHY、抓包或从机报告的连接间隔、传输字节数,以及**发送端完成**和**接收端校验完成**两个时间戳。少了后一个,你测的是自己的缓冲区,不是链路。

## 这些数字从哪来

- Bluetooth Core 规范:ATT 头(操作码 + 句柄)、L2CAP 基本头、链路层报文格式、前导与 CRC 长度、带 DLE 的 251 字节链路层 PDU 上限,以及"加密链路的 PDU 长度包含 MIC"这条规则。
- Nordic 的吞吐应用笔记:帧间隔与确认的记账方式。
- 平台约束(`maximumWriteValueLength`、`canSendWriteWithoutResponse`、Android 14 首次请求 517 字节 MTU)来自平台文档,不是实测。
